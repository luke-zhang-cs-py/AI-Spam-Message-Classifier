AI-Spam-Message-Classifier · port 5002

Spam or ham, and which words decided it

A TF-IDF classifier with three ways in — two scripts, one self-contained file, and a web page that shows the per-word contribution behind every verdict. All three drive the same pipeline. The interesting part of this project is not the accuracy figure; it is the reasons that figure should not be trusted, which are on this page rather than buried.

Repository Open app (local)

The result, and the three reasons to distrust it

Both models, scored on the same held-out split. Read the table, then read what is under it — the numbers are real, and they describe this dataset rather than the world.

A 25% split of 81 messages. One test message is worth percentage points of accuracy.
ModelAccuracyPrecision RecallF1Confusion

1. The two models are tied, and that is the finding

They do not merely score the same — they produce the identical confusion matrix, so they make the same call on all 21 test messages, and miss the same two. Two very different algorithms agreeing perfectly is a symptom of the data, not a strong model: the spam here is separable by obvious keywords, so almost any classifier lands in the same place.

2. "Best model" is a coin toss

The trainer compares with f1 > best_score and iterates Naive Bayes first, so on a tie the first one wins. It reports Naive Bayes as best. That is the iteration order presented as a result.

3. The dataset is 81 messages

40 spam, 41 ham, and written rather than collected — clean, unambiguous, and free of the obfuscation real spam uses (Fr33, unicode lookalikes, image-only payloads). The metrics will swing noticeably if you change random_state.

What it does get right

No false positives: no real message was called spam, at the cost of missing 2 of 10 spam. For a spam filter that is the right side to err on — a missed spam is an annoyance, a misfiled real message is a lost message.

Why it said that

The part the command line cannot give you. Both classifiers reduce to a linear score over TF-IDF features, so a token's contribution is its TF-IDF value times the model's weight for it — and the page colours each word by which way it pushed. 


  

    The two models keep that weight in different places —
    coef_ for logistic regression, the difference between the
    two rows of feature_log_prob_ for Naive Bayes — and
    token_weights() handles both, so the explanation does not
    depend on which model happened to win the tie.
